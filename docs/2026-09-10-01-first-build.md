# Plan — the first build

Status: 2026-09-10. **Historical.** Everything listed as open here was built the
same day — the Wikidata join, the D1 load, the Worker, the published database.
Kept for the failures it records, which are still worth reading: a streaming
parser that silently returned 56 of 5,308 rows, and dr5hn translating Brazil's
state of Acre as the unit of area.

## What works, with the numbers it produced

```
places stage --sample     3 sources, 9.5MB
places extract            countries      280 places   21,280 names   76 languages
                          subdivisions 5,308 places  103,178 names   29 languages
                          cities      34,135 places    7,097 names    1 language
places merge              countries         18% romanised
                          subdivisions      41% romanised
                          cities           100% romanised
```

Cities show one language and 100% romanised because `--sample` deliberately skips
`alternateNames.zip` — 193MB compressed, ~900MB expanded. A full `places stage`
fills them.

`places report` separates *named* from *translated*, which is the number that
matters:

```
  locale      countries (280)      subdivisions (5308)
  ar*   100% / 100% translated   100% / 98% translated
  ja*   100% / 100% translated   100% / 99% translated
  ru*   100% / 100% translated   100% / 98% translated
  de    100% /  59% translated   100% / 24% translated
  nl    100% /  59% translated   100% / 25% translated
  vi    100% /  36% translated     1% /  0% translated
```

Arabic, Japanese and Russian subdivisions are genuinely translated at 98–99%.
German and Dutch sit at 24–25% because the rest are the English string, correctly
demoted to `romanised` — which for a Latin script is the right answer and for a
non-Latin one would not be. Vietnamese has almost no subdivision data at all;
dr5hn does not carry it.

## Now loading into a real database

`places load` writes `.build/load.sql` — 39,719 places and 131,554 names, 12MB —
and `wrangler d1 execute places --local --file=.build/load.sql` applies it. The
cross-language case the whole project exists for now answers from SQL:

```
Brazilian states, for a Japanese reader     Acre → エーカー   Alagoas → アラゴアス州
                  for an Arabic reader      Acre → فدان      Alagoas → ألاغواس
```

Two things that cost an hour each and would have cost a day later:

**Foreign keys are ordered, not optional.** Batching places and names in one pass
emits a name batch whenever it fills, sometimes before the batch holding its
place, and D1 answers `FOREIGN KEY constraint failed` while naming no row. Two
passes — every place, then every name. `PRAGMA foreign_keys=OFF` would also have
silenced it and would have been the wrong fix: the constraint was right.

**Four subdivision ids arrive twice.** dr5hn lists Guyane, Saint-Pierre-et-
Miquelon, Saint-Barthélemy and Saint-Martin as both French subdivisions and
entries of their own. First occurrence wins and the count prints on every run,
because four is upstream being reasonable and four hundred would be a source that
had changed shape.

## What the data is actually like

Look again at that Japanese column. **Acre is `エーカー` — the unit of area.** In
Arabic it is `فدان`, also the unit. dr5hn's translations are machine-produced, and
where a place name collides with a common noun the machine sometimes takes the
noun. California and England are correct in every language checked, so this is a
tail and not a pattern — but it is exactly why `kind` says `translated` rather
than `correct`. It records that a source called this a translation. It has never
meant a human read it.

Worth knowing before anyone proposes dropping the `source` column: the day someone
wants to fix Acre, being able to ask which source said that is the difference
between a correction and an argument.

## A correction: cities are not translated, and the earlier figure was measured wrong

The plan this repository came from claims Wikidata gives **84% Japanese and 89%
Russian** for cities of 15,000–100,000 people. Building the label join disproved
it, and the mistake is worth writing down because it is an easy one to repeat.

That figure came from asking Wikidata: *of cities with a population statement
between 15k and 100k, how many carry a `ja` label?* It answered 84% of 6,451
items. **GeoNames has about 30,000 real cities in that band.** So the question had
silently been narrowed to the fifth of them Wikidata knows well enough to have
recorded a population for — and an item somebody curated a population onto is
exactly the item somebody curated labels onto. The number was true and measured
the wrong population.

Asked against a real inventory instead — 400 Brazilian cities from
`cities15000`, matched to Wikidata by `P1566` (305 of 400 matched, so the join is
sound):

```
  en   296 / 400   ██████████████████████
  pt    10 / 400   █
  de     6 / 400
  ja     3 / 400
  ar     2 / 400
  ru     1 / 400      zh 1     th 1     vi 1
```

**Three Japanese labels. One Russian.** Even Portuguese — the local language —
manages ten, because a Wikidata *label* is not a Wikipedia *article*, and
municipality items are imported with an English label and left there.

### What this changes

**Cities are not a translated tier and cannot be made into one from open data.**
Countries are complete, subdivisions are genuinely good in the languages dr5hn
carries, and cities get a romanised name and, for most places in most languages,
nothing else. Anyone promising otherwise has measured a subset.

For Latin-script readers that is fine — "Ourinhos" is what a Portuguese, German or
Vietnamese reader would write anyway. For Thai, Japanese, Korean, Chinese, Arabic,
Russian and every other non-Latin script, it means **Latin characters inside their
sentence for essentially every city**.

So **transliteration stops being a deferred nicety and becomes the only answer
that exists for cities in non-Latin scripts.** It was already designed for — the
`kind` column, names addable per (place, locale), real names winning by rule — but
it should now be understood as load-bearing rather than optional. The design
survived the correction; the priority did not.

The label pass stays: 296 English labels per 400 cities is a better English name
than GeoNames' ASCII, subdivisions and countries benefit, and the day Wikidata
fills in it will be a re-run rather than a rebuild.

## What is not built

- [ ] **The Wikidata label join.** The one source that translates cities
      cross-language — 84% `ja` and 89% `ru` for cities of 15k–100k, where GeoNames
      manages 7% and 20%. Joined on `P1566`, or on GeoNames' own `wkdt` rows,
      whichever proves denser. Its SPARQL endpoint times out on wide queries, so
      this needs batching and a policy for which languages to fetch.
- [ ] **The D1 load**, and the migration that creates the schema in `src/db`.
      Batched inserts through the binding; `wrangler d1 execute --file` for the
      first bulk load, because it does in one command what a Worker cannot do at all.
- [ ] **The Worker** implementing `src/api/contract.ts`, with the OpenAPI document
      generated from the same contract.
- [ ] **A published sample database**, committed, so the repository is useful on
      clone and so ODbL's share-alike is satisfied by the rows being present rather
      than by the ETL that would produce them.
- [ ] **Transliteration.** Deferred by decision, and the schema keeps it possible:
      `kind` distinguishes it, names are addable per (place, locale) without an ETL
      rerun, and real names beat generated ones by rule. The hole it fills is `th`,
      `zh` and `ko` below 100,000 people.

## Decisions already taken

| Question | Answer |
| --- | --- |
| Languages | **Every one the sources carry.** No locale list; `locale` is a request parameter. |
| Wikidata's languages | The exception — one SPARQL pass per language, so this service sets its own policy rather than inheriting a consumer's. |
| Licences | Code MIT, data ODbL-1.0, stated separately. The derived rows must be published, not only the ETL. |
| Cities as a vocabulary | No. A table with a parent, searched by prefix. 152,970 rows is not an enum. |
| Where the ETL runs | First load from a machine; the recurring refresh as a cron Workflow with R2 staging, because a public dataset that needs a maintainer's laptop goes stale. |

## One thing found while building

`scripts/lib/ndjson.ts` streams a large JSON array by tracking brace depth. The
first version rescanned each chunk from index 0, which re-applied its
inside-a-string toggles to text it had already read — so braces inside data were
counted as structure. It parsed **56 of dr5hn's 5,308 rows and reported success**.
A `scanned` index fixed it. Worth knowing because the failure was silent and the
output looked plausible: a streaming parser that is subtly wrong does not crash,
it just quietly returns less than it should.
